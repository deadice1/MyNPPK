# Ролевая модель доступа

В приложении реализована жесткая проверка прав доступа на уровне интерфейса.

## Список ролей

1. **student** (в коде роль `1`)
   - Видит только вкладку своего расписания.
   - Не имеет доступа к управлению подписками на предметы.
   - Кнопка "Режим учителя" для этой роли вырезана из кода.

2. **teacher** (в коде роль `2`)
   - Видит кнопку "Режим учителя".
   - Может настраивать свои подписки на разные группы и предметы.
   - Имеет возможность переключаться между личным расписанием и общим списком групп.

## Реализация контроля

### 1. Сохранение роли
При входе роль сохраняется в `SharedPreferences`:
```kotlin
prefs.edit().putString("user_role", roleName).commit()
```

### 2. Проверка в UI
Перед открытием модуля Schedule, хост-приложение запрашивает роль:
```kotlin
val isTeacherRole = authRepository.getCachedRole() == "Преподаватель"
navigator.open(MainTestScreen(isTeacherRole = isTeacherRole))
```

### 3. Блокировка функций
Внутри `MainTestScreen.kt`:
```kotlin
if (isTeacherRole) {
    // Отображаем кнопку переключения режимов
    Button(text = "Режим учителя", ...)
}
```
Даже если злоумышленник попытается вызвать `TeacherContent`, данные не будут загружены корректно без валидного `userId` преподавателя в сессии.
